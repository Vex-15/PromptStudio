Under the hood

How itworks

A rough prompt goes in. One neural net and one rule rubric analyse it independently, a fusion step merges what each found, and you decide whether the result is actually better. No LLM rewrites anything. all local, all deterministic.

01Overview

Prompt Studio is a local workshop for one job: turning a vague prompt into a specific one. It runs two analysers that know different things, then fuses them. 

raw prompt
   |
   |-- rule engine (LangChain LCEL)  ->  score /100, diagnosis, structured rebuild
   |-- neural engine (BiLSTM+attn)   ->  task class, 5 gap probabilities, templates
   |
   v
fusion: pick the right backbone, one owner per section, dedupe, keep TASK verbatim
   |
   v
merged prompt  +  re-grade by both engines  +  residual gaps  +  your vote

Three rules shape everything:

  • The original prompt is never edited. It is kept verbatim as the TASK: line; only missing parts are appended, so intent cannot drift.
  • Nothing is guessed silently. Safe defaults are labelled as assumptions; things only you know (context, purpose) become bracketed placeholders and explicit questions.
  • Every rewrite is explainable. The rule engine reports which points it awarded, the neural engine reports per-part probabilities and attention weights.

Everything runs in one Python process on 127.0.0.1:8000. The trained model (1.2 MB) ships with the project, so there is no training step and no API key. The only optional network feature is running the two prompts on a local Ollama model for comparison.

02The problem it solves

Most weak prompts fail in the same five places. The project models exactly these as five binary labels — one per part that can be missing:

GapWhat is missingTypical fix
contextproject, language, environment, backgroundassumed language or a placeholder
audiencewho reads the outputa reader level, from your setting
constraintslimits, errors, style, exclusionsexplicit constraints
output_formatshape of the answerone code block, table, bullets…
purposewhat it is fora placeholder + a question

The two engines answer different questions about the same text. The rule engine asks “what is measurably absent, and what is measurably present?” with regex evidence and a weighted rubric. The neural engine asks “what kind of request is this, and which parts look absent in this kind of request?” with a learned classifier. Neither is sufficient alone: the rubric can be gamed by keywords but is auditable; the classifier generalises across tasks but cannot explain a score.

03The neural engine

A bidirectional LSTM with attention pooling and two heads, trained from scratch on synthetic prompts. Multi-task, because the task type and the missing parts inform each other. 

tokens -> Embedding(100) -> BiLSTM(128) -> masked attention pooling
                                                   |-- task head  6-way softmax
                                                   |-- gap head   5 independent sigmoids
                                                   '-- attention weights (explanation)

Data

src/generate_dataset.py builds prompts from a core task plus optional components (context, audience, constraints, format, purpose). Labels come free: a component that was not added is “missing”. It adds typos, casing changes and filler so the model does not just memorise templates. Splits: train / val / test, plus data/manual_test.csv — 40 hand-written, hand-labelled prompts that the model never saw, which is the realistic number.

Text pipeline

Lowercase, keep [a-z0-9']+ tokens, drop punctuation, truncate to 64 tokens. The vocabulary is built from training text with a minimum frequency of 2, with <pad> and <unk> reserved. During training, 10% of tokens are randomly replaced with <unk> (word dropout) as regularisation.

Hyperparameters

SettingValue
max tokens64
embedding / hidden100 / 128 per direction
dropout / word dropout0.3 / 0.1
batch / epochs / patience64 / 25 / 5 (early stop)
optimiser / lrAdam / 2e-3, gradients clipped
gap threshold0.5 probability
template confidence floor0.70, else the generic template

Training objective

A single shared encoder optimised on two losses at once: cross-entropy for the six-way task classification and binary cross-entropy for each of the five gap labels. The gap head is multi-label, not multi-class — a prompt can lack several parts simultaneously.

Attention as explanation

Attention scores are masked so padding contributes nothing, then softmaxed across tokens, giving weights that sum to 1. Those weights drive the pooling and the UI heatmap: the words the model leaned on. They are a diagnostic view of the model's focus, not a causal proof of its decision.

Rule safety net

Regexes can prove some parts are already present, so the hybrid removes those from the model's “missing” list and reports the override. Evidence accepted: a word/line limit (“under 200 words”) or a stated tone proves constraints; a format phrase (“as a table”, “json”, “bullet points”) proves output_format. This catches the model's confident false positives without letting it invent evidence.

Templates

Each (task, gap) pair stores either a safe default — added, and labelled as an assumption — or a placeholder in brackets, which also becomes a question in the UI. Only the user knows context and purpose, so those are always placeholders. If task confidence is below 0.70 the generic template is used rather than applying a wrong task's advice.

04The rule engine

A deterministic grader and rebuilder for programming prompts, orchestrated with LangChain's LCEL. Every stage is a Runnable; independent detectors run in parallel through RunnablePassthrough.assign, and batch scoring uses .batch(). No model is involved. 

prompt
  |-- injection? --|-- intent? --|-- features? --|   (parallel assign)
  v
score (rubric) -> diagnose -> decide strategy -> rebuild -> re-score -> drift guard

Feature extraction

Scoring only ever sees checkable booleans and counts, never the raw text: language, libraries, presence of code or an error message, filler count, vague words, number of mixed tasks, contradictions, repetition, environment/version, data, purpose clues, described inputs/outputs, concrete nouns, list structure, format cues, error handling, performance, style, exclusions, reproducibility, tests.

Diagnosis

Issues come with a severity. High: injection patterns, too short to infer a task, contradictory requirements, “fix this code” without code. Medium: no language, no described inputs/outputs, no output format, no constraints, vague words, several tasks in one request, unsupported guarantees, version-sensitive requests. Low: filler and repetition. Questions are added only where the answer changes the result.

Strategy

ScoreStrategyWhat happens
> 85nonetrimmed only; already strong
60 – 85standardtargeted sections; only weak dimensions get text
< 60advancedthe above plus step decomposition and a validation section
anybasic (manual)compression only: filler removed, spacing fixed

Rebuild and drift guard

The rebuild keeps your task text as the TASK section, adds a CONTEXT (assumed language if none was named, plus the reader level), REQUIREMENTS for the detected intent, CONSTRAINTS including “use only real, documented APIs”, and OUTPUT FORMAT. The merged text is re-scored, then a drift guard checks that at least 90% of the key terms survived, the intent is unchanged, and no injection pattern is present. Tokens are estimated at four characters per token.

05Fusion: how the two become one

The rule engine only knows how to rewrite coding prompts. The neural classifier is what tells fusion whether that rewrite applies — so a story prompt never receives “state the function signature”.

  1. Run the rule engine for a score, a diagnosis and structured sections.
  2. Run the neural engine for task class, gap probabilities and per-task additions.
  3. Choose a backbone. Rule rubric if the neural task is coding or the rule intent is debug / refactor / test; otherwise the neural templates drive.
  4. Merge section by section (table below). One owner per section: two competing output-format instructions in one prompt is worse than one.
  5. Dedupe. A new line is dropped if it is a near-duplicate of an existing one (token-set Jaccard similarity above 0.5).
  6. Re-grade both engines on the merged text to report the score after fusion and any gap still open.
SectionWho supplies itRule
TASKyoualways the original prompt, verbatim
CONTEXTbothrule context plus neural context if not a duplicate
AUDIENCEneuralskipped when the rule engine's “Reader:” line already exists
REQUIREMENTSrule (or fusion)rule wins; advanced adds a step-decomposition line
CONSTRAINTSrule (or neural)rule wins if it produced constraints, else neural
OUTPUT FORMATrule (or neural)one consistent spec, never both
PURPOSEneuralplaceholder + question
VALIDATIONfusionadvanced mode only

Worked example

Input: write python code for student marks. The neural classifier says coding (70% confidence); the rule engine scores it 40/100 and detects the code-generation intent. The rule backbone supplies the sections, and fusion reports 40 → 80, three of five gaps addressed, about 9 → 204 estimated tokens. Purpose stays open because neither engine can know it: 

TASK:
write python code for student marks

CONTEXT:
- Reader: working developer; keep explanation brief and precise

REQUIREMENTS:
1. State the function or module signature with input and output types before the code.
2. Include one short usage example.
3. Work in steps: restate the problem and assumptions, outline the approach, write the
   code, then check it against 2-3 examples.
4. Include 3 test cases.

CONSTRAINTS:
- Handle invalid input and errors explicitly.
- Use only real, documented APIs. If unsure a function exists, say so instead of inventing it.
- Add concise comments; avoid unexplained external dependencies.

OUTPUT FORMAT:
- One runnable code block, then a short explanation (max ~150 words).

VALIDATION:
- Re-check the result against every requirement above and list anything you could not meet.

A non-coding prompt such as write something about ai in education flips the backbone: the classifier says writing, so the writing templates supply context, audience and purpose placeholders and no code advice appears. With basic mode fusion only compresses — useful when you want a trim, not a rewrite.

06The score and the gap model

The 100-point rubric is deliberately mechanical: every point is earned by a specific, checkable feature. It is a heuristic, not a validated human rating.

DimensionMaxEarned by
clarity20≥3 words (6), an action verb (6), few vague words (up to 4), a single task (4), contradictions −6
context20language 8, library 5, environment 3, purpose or data 4
specificity20inputs/outputs 6, concrete terms 5, list structure 5, length 4
output15format cues ×5 each, capped at 15
constraints15errors 4, performance 3, style 3, exclusions 3, reproducibility 3, tests 2
efficiency1010 − 2×filler, − repetition, − over-long prompts

What the gap probabilities mean

Each of the five parts gets an independent sigmoid: the probability that the part is missing. Above 0.5 it counts as missing; the UI shows the raw value so you can see marginal calls. The gap head is trained on synthetic labels, so treat the numbers as signals from a small model, not calibrated probabilities.

Task classes

coding, writing, summarization, explanation, analysis, brainstorming. The class selects the template set, and it is the gate that decides whether the rule engine's coding structure is appropriate.

07Human in the loop

Scoring is automated; preference is not. Every analysis ends with the original and the merged prompt side by side — scores, estimated tokens, open gaps and the change list — and an “I’d use this” button on each card.

  • One vote per analysis, so repeated clicks cannot inflate the tally.
  • The choice is appended to artifacts/preferences.jsonl, one JSON object per line: prompt, merged text, choice, both scores, driving engine, timestamp.
  • A running tally is shown under the comparison and reloaded on start; delete the file to reset it.
  • Votes are local and are not used to retrain or re-score anything.

This answers a different question from the rubric. The rubric says whether the merged prompt satisfies the rubric; the votes say whether a person would send it.

08Measuring the fusion

python -m src.evaluate_fusion runs original → merged for every prompt in a set, re-grades with both engines, and writes artifacts/fusion_results.md plus JSON. Measured on the 40 hand-written prompts (mode auto, level developer):

MetricResult
average score35.45 → 63.17 / 100
average gain+27.73 (median +27.5, range +11 to +52)
improved / unchanged / regressed40 / 0 / 0
intent preserved40 / 40 (100%)
estimated tokens16.1 → 155.0 (20.35×)
gaps addressed3.02 / 5 (1.02 still open)
engine splitneural 31, rule rubric 9

By detected task: coding +31.3, analysis +29.1, brainstorming +27.7, explanation +27.3, writing +25.7, summarization +24.4 (average gain).

The rubric that scores “after” is the same one whose diagnosis drives the rewrite, so part of the gain is self-fulfilling. Key-term coverage is 100% by construction, because the original prompt is always included as TASK. The 20× token growth is a real cost. Read the gain as “satisfies the rubric much better”, and use the human votes for the other question.

09API

The frontend is static HTML/CSS/JS served by FastAPI; every interaction is a JSON request. No authentication, because the server binds to loopback only.

POST/api/batch{prompts[], mode, level} → rows + summary

curl -s -X POST http://127.0.0.1:8000/api/analyze \
  -H "Content-Type: application/json" \
  -d '{"prompt": "write python code for student marks", "mode": "auto", "level": "developer"}'

The response carries combined (text, sections with their source, addressed and residual gaps), score (before/after/delta and both dimension vectors), neural (task, confidence, task probabilities, gap probabilities, attention, tokens, its own rewrite) and rubric (dimensions, issues, questions, changes, drift, tokens, versions, its own rewrite).

11Limits and honest notes

  • Synthetic training data. The neural model learned from generated prompts; manual_test.csv is the realistic number, and 40 prompts is small.
  • Templates, not generation. Rewrites are assembled from fixed templates and rules, so output is consistent rather than creative.
  • The rubric is a heuristic. It favours the sections the rewriter adds, which is why the automatic gain needs the human votes beside it.
  • Short prompts only. The model truncates at 64 tokens; long briefs lose information before classification.
  • English patterns. Rule vocabularies, language detection and templates are English-oriented.
  • Injection detection is a warning. The regex catches common “ignore previous instructions” patterns; it is not a security boundary.
  • Local by default. The only outbound calls are the optional Ollama request to localhost:11434 and Google Fonts for typography.
